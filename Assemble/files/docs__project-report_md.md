## 5 · Source-order coverage tour

### Team

Fields remain names/roles/contact/contribution placeholders. Fill only actual roles and work with authentic commits/PRs. The baseline is Codex-assisted; none of the four learning stages retroactively gives its code authorship to a student.

### Introduction and objectives

Describes central student/admin sports operations and mandated HTML/CSS/JS/PHP/MySQL with responsive/security/API extensions. Rephrase in the team’s own understanding; do not invent institutional deployment or user research.

### System description

Links architecture and maps all topic 3 features to implemented screens. The mapping is an orientation table, not test evidence. New Assemble traceability adds exact source/route/test/owner/video/completion fields. Distinguish current generic standings/individual registration from future sport-specific bracket functionality.

### Screenshots

Use real application captures and synthetic identities. Existing screenshots may be a starting point, but final submission needs captures of the actual release/host. Enrollment must not reveal manual setup key, one-time recovery values, passwords, cookies or real student records; use surrounding safe states instead.

### Validation

Legacy numbers are previous workspace results, not a student’s own execution or this task’s current regression. Cite dated evidence and separately record current safe checks, skipped database/browser suites, and future production validation.

### Required links

Repository, live hosted app and demonstration video fields are genuinely unfilled. Repository URL can be factual; lecturer access/public status must still be verified. Never fill hosted/video fields with invented domains or fake short links.

### Demonstration sequence

Eight suggestions cover login/2FA, membership approval, sessions/tournament/history, CRUD/scores, booking collision, attendance/reports and relational/security explanation. It is a rehearsal order, not proof any person performed or authored it.

### Submission checklist

Export PDF/Word, verify lecturer access, leader/designated submission and deadline to be confirmed. Do not invent a submission date or mark teamwork completed by assigning generated folders.

## 10 · Security, correctness and accessibility

Redact real identities and authentication material from screenshots. Confirm imagery rights. Share contact information only as required by the course and with appropriate consent.

For documentation, keep supported Markdown, meaningful link labels and diagrams whose meaning does not depend on color alone. For configuration, preserve the application trust boundaries rather than hiding failures in UI.

## 11 · Common mistakes and diagnosis

Fake author claims violate integrity. Historical counts presented as fresh are misleading. Localhost in live URL field is inaccessible to lecturer. Unlisted video can still expose secrets. A feature list without route/test evidence cannot establish completion.

## 12 · Read or run safely

Markdown rendering is not report export. Read the rubric and traceability, then fill real fields and export manually. Verify every final link with an authorized viewer.

These are teaching instructions. Actual outcomes, including skipped suites, are centralized in [the current evidence register](../16-evidence-and-artifact-register.md). Do not relabel a legacy or suggested command as freshly passed.

## 13 · Debugging lesson

Trace the consumer named in section 4 and verify one boundary at a time. Record filenames, versions, route/status, rule names or synthetic counts. Do not dump resolved configuration, private env files, request cookies, factor values or identity-bearing SQL exports. Diagnose the first failed prerequisite before retrying.

## 14 · Guided experiment

Choose one report feature and supply actual file, route, test reference and safe screenshot location in a private draft. Leave unknown deployment/video/identity fields TODO.

Keep an observation worksheet outside the public webroot. If you later make a temporary source edit, save your own small patch first, then manually undo only your lines; never overwrite another contributor's shared work or reset a real database for a lesson.

## 15 · Challenge ladder

- **Understand:** explain section 6 using the source and identify its actual consumer.
- **Modify:** propose one narrowly scoped clarification or correction only after reproducing a misunderstanding; coordinate with the source owner and verify its linked contract.
- **Engineer:** evaluate one failure in section 11, describe its evidence and trade-off, and submit genuine reviewed work through the human workflow after authorization.

Expected evidence is a correct source-to-behavior explanation and any real test result, not a cosmetic commit or copied screenshot. The experiment in section 14 supplies the safe setup; future changes must have their own focused validation.
